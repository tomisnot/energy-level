# 多体架构审查（2026-10-30）

后续整理的现行接口与能力边界见 [多体接口与维护约定](多体接口与维护约定.md)。以下保留整理前的审查证据。

## 结论与范围

当前多体代码有可继续发展的分层基础，但公共接口的一致性已经落后于功能增长。优先工作应是修复物理语义与配置接线、统一输入输出契约、补入口回归，而不是整体重写或单纯拆文件。

本次检查针对当前工作区，包含已有未提交修改和未跟踪模块，不代表某个已发布提交。阅读范围包括 `src/core/manybody/`、公共 runspec/protocol、多体 GUI、相关 checks，以及部分 AI 执行入口。多体目录当前有 27 个 Python 文件、约 7103 行；没有对每个算法做完整数学证明，也没有进行大系统性能认证。本次仅新增此报告，未修改实现。

## 已有基础应当保留

- `model.py` 表达原子、几何和局部参数，`assemble.py` 做物理标定，求解器执行数值计算；ARC 标定与数值执行分离是合理的。
- 公共 `runspec.build_run/evolve_run` 为 GUI/AI 提供了共享核心路径。
- `hamiltonian_plan.py` 已开始表达受限基空间，`matrix_free.py` 支持无需全空间矩阵的算子作用。
- `state.py` 已抽出初态与 MPS 接续，`observables.py` 已抽出公共观测量。
- 有 ED 参照、跨后端小系统比较、固定荷与状态接续回归。应在这些基础上逐步整理。

当前主要依赖链：

```text
GUI / AI / Python 调用
        ↓
schema / protocol → runspec.build_run
        ↓
含时 runspec_mb / 平衡态 eq_engine
        ↓
model → calibrate → calib + HamiltonianPlan
        ↓
含时分派表 / 平衡态 eq_route
        ↓
数值后端 → 字典结果 → 摘要 / GUI / Web / 存档
```

问题发生在箭头处：同一能力被重复描述，同一参数沿不同路径传递时含义或有效性发生变化。

## 需要先修复的问题

### 1. 周期边界没有进入标定缓存键（高优先级，已复现键冲突）

位置：`src/core/manybody/runspec_mb.py:43`，`src/core/manybody/assemble.py:218`。

模型已经支持 `periods_um`，标定距离使用周期最小像，但 `_calib_key` 未包含周期长度。

验证：两原子在 `(0,0,0)`、`(9,0,0)`，无周期时 R=9 μm；周期 `(10,10)` 时 R=1 μm。两个模型得到完全相同的标定缓存键 `9c557b94836d0d00`。因此同进程切换边界条件时可能命中另一几何的标定结果。这次验证了几何和键冲突，没有运行 ARC 重新标定。

建议：从规范化的完整标定输入生成键，显式区分只影响驱动与影响标定的字段；增加“改变每个标定相关字段会使缓存失效”的回归。

### 2. 后端声明、参数转发和执行分派不一致（已复现）

位置：`schema_mb.py:70`、`runspec_mb.py:217`、`runspec_mb.py:249`、`runspec_mb.py:284`、`src/core/runspec.py:80`。

- schema 与配置解析支持 `tdvp-single`、`tdvp-adaptive`，公共 `_ENGINE_TABLE` 缺少二者；调用 `engine_fn` 均得到“未知引擎”。GUI 的含时选项也独立维护，没有这两个选项。
- 指定 `manybody.max_step_ns=0.123`，`swap-tebd-gpu` 构建出的 engine_kwargs 没有该键。其默认步长会根据输出时间间隔确定，因此用户的积分精度控制没有生效。
- 指定 `manybody.chi_max=42`，PEPS 与 trajectories 的 engine_kwargs 均没有该键，仍使用各自后端默认值；`truncerr` 也未在这些分支统一转发。
- GPU MPS 有 `memory_budget_mb` 形参，但产品构建路径未传入该配置；PEPS 则已映射到 `max_intermediate_mb`。

参数转发检查使用合成 calib、替换标定函数，只验证真实 RunSpec 构建逻辑，不需要运行大规模求解。

建议：建立小型后端能力登记表，由其提供规范名称、别名、入口、可用任务、可接收选项和默认值；schema/GUI/路由使用同一份声明。不要继续在多个 if 分支中手抄名单。

### 3. 不支持的输入被 `**kwargs` 静默吸收（部分已数值复现）

位置：`src/core/runspec.py:691`、`classical_spin.py:65`、`engine_trajectories.py:65`、`engine_peps.py:166`。

公共含时入口统一传入 `segments`、`plan`、`progress_arr`、`log`。经典自旋、轨迹、PEPS 的函数签名没有显式接收其中部分参数，而是通过 `**kwargs` 接收；当前实现未消费 `segments`，也未统一处理进度和取消。

数值验证：单原子、初态 g、演化到 100 ns，基础 Ω=0，分段从 t=0 指定 Ω=1 MHz。经典自旋返回最终布居 0；直接传相同的静态 Ω=1 返回约 0.0954915。分段配置被接受，但没有作用。

建议：构建阶段进行能力校验。不支持分段驱动就明确拒绝，不能解释为“使用静态驱动”。统一的进度/取消对象由适配器传入；后端特有选项使用明确字段，拒绝未知选项。Python 直接调用也应保留必要校验。

### 4. 投影基计算破坏原子身份和结果契约（已复现）

位置：`hamiltonian_plan.py:100`、`observables.py:17`、`engine_ed.py:435`、`eq_route.py:379`。

公共基矢约定使用 `n-1-i` 位代表原子 i；投影含时和投影基态布居却使用 `i` 位，导致原子顺序反转。

三原子链、PXP 边 `[[0,1],[1,2]]`、初态 `rgg` 的验证：

- t=0 的 `pops_atom` 返回 `[0,0,1]`，应为 `[1,0,0]`。
- 同一结果的公共 `sz` 为 `[-1,1,1]`，依现有 g/r 约定，它正确指向第一个原子；两个观测字段相互矛盾。
- `pops.shape=(2,3)` 是逐原子布居，但 `states` 长度为 5，内容是受限联合基矢；标签与数据列不匹配。
- `psi0='ground'` 在特殊处理前先进入一般字符串解析，报“初态串长度须=3”。
- `S` 被填为全零并在 note 中解释未计算。这会让只读数据的绘图器把“未计算”画成“没有纠缠”；受限态并非不能定义纠缠熵，只是这里没有实现对应计算。

建议：建立共享 Basis 描述，集中处理基矢编号、原子顺序、投影索引和观测映射。联合态概率与逐原子布居分字段；未计算的量不输出数值零。

### 5. 特殊算法的适用条件没有被入口完整检查（已复现）

位置：`eq_route.py:339`、`free_fermion.py:10`。

自由费米子后端检查耦合项和邻接范围，但入口未检查 `system['Om']`，调用的求解函数也没有 Om 参数。非零局部翻转驱动被忽略。

验证：三个无耦合原子，terms 为 I2，Ω 全部为 1 MHz，δ 全零。同一输入 ED 得到 E0≈−1.5 MHz，自由费米子路径返回 0。后者应拒绝这个超出适用域的模型。

补充静态发现：产品配置构建强制 terms 全开，而自由费米子判据拒绝 terms 中含 I3；底层可用能力与产品输入之间还需明确对应关系。

建议：适用条件应检查规范化后的实际 Hamiltonian，而非只检查后端名称或部分模型标签。入口先返回支持/拒绝及原因，拒绝后不得继续给出另一问题的数值结果。

### 6. 资源控制没有覆盖所有计算路径（静态确认，未做大系统压测）

位置：`eq_route.py:415`、`engine_ed.py:445`、`hamiltonian_plan.py:50`、`cost_mb.py:34`、`runspec_mb.py:217`。

- DOS 即使选择 KPM/GPU-KPM，也先将 H 稠密化并做完整 `eigvalsh` 来定谱界，抵消 KPM 的规模优势。
- 投影 ED 先分配全空间初态，再无条件把受限 H 稠密化并对角化，没有复用普通 ED 的稠密/稀疏阈值。
- 约束基生成和显式边的成本预估都遍历 `2^N`，预估本身可能成为重任务。
- 含时 `resolve_solver` 在构建 plan 前按全空间 `2^N` 选择后端，之后才检查投影；没有把有效维数真正纳入这一决策。

建议：先得到带资源上限的 Basis/Plan 描述，再做可行性判断；大型谱界使用迭代估计或可靠边界，统一限制稠密化、基枚举和输出数组预算。

### 7. 已弃用参数仍以有效参数形式向 AI 暴露（已复现）

位置：`schema_mb.py:31`、`runspec_mb.py:78`、`model.py:30`、`src/ui/ui_manybody.py:613`。

schema 和部分 docstring 仍承诺 template 决定预设、显式 terms 优先；产品 `model_from_params` 已改成 I1/I2/I3 全开。传入 `[]`、`['I1']`、`['I2']` 都得到全部三项。

这是“全相互作用”产品决策与旧契约未同步的问题，并不建议擅自恢复旧开关。应该决定并明确：产品不再支持的键从可设置 schema 移除，旧存档迁移时给出提示；底层研究 API 若仍支持 terms，应明确其与产品模式的区别。

GUI 也保留了一组旧 terms/template 控件处理函数。应核实调用关系后删除失效代码，并清理声称“唯一事实源”“不静默”等但与实现矛盾的注释。历史文档保留为历史记录，当前能力说明应以代码和回归为准。

## 建议统一的边界

### 输入：统一物理问题，分开数值选项

保留现有外部配置兼容入口，内部规范化为以下几部分即可，不必一开始引入庞大类层次：

1. **模型**：site_id、位置、局部空间、驱动、耦合、边界条件、单位。
2. **任务**：时间演化/基态/热态/谱，初态，时间或参数轴，所需观测量。
3. **基空间与约束**：full/projected/固定荷、基矢顺序、索引映射。
4. **求解选项**：精度、步长、χ、随机种子、内存预算、硬件。

`HamiltonianPlan` 应逐步成为共同的物理输入描述，但不要要求所有后端都编译成 CSR。CSR、LinearOperator、MPO、局部门和经典有效场应是同一物理问题的不同表示。

当前 I1/I2/I3、复共轭和位序逻辑在 sparse 装配、投影编译、matrix-free、MPO、GPU/PEPS 局部门等处重复。应共享项的语义与基约定，保留性能相关的不同编译实现，并用复耦合、不对称小模型检查等价性。

### 输出：统一数据语义，不强迫统一数组形状

建议逐步增加版本化元信息：quantity、axes、unit、site_id/basis_id、approximation、uncertainty 和 validity。

- 联合基态概率：`(time,basis)`；逐原子占据：`(time,site)`。不要用同一个 pops 字段让消费者猜。
- 矩阵关联：明确两轴的身份与顺序；复值量保留复数语义。
- 基态/热态：区分能量、能隙、温度轴、误差估计，不能把未求得的量伪装为数值零。
- 物理损失、轨迹存活权重、数值范数漂移分别命名，不能都依赖 loss 的隐含解释。
- 原生 state/checkpoint 与可展示的观测数据分开，统一说明状态所处基空间与后端格式。
- diagnostics 可扩展，但明确 requested/resolved backend、近似类型、收敛状态、实际使用的参数与警告。

这样 GUI/Web 能按数据种类绘图：时序曲线、矩阵热图、带误差的曲线、原子二维点阵上的标量场。算法身份只是来源信息。

### 后端：公共适配层薄，算法内部保持独立

用明确能力表统一 aliases、任务、初态种类、分段驱动、投影、耗散、返回态与硬件要求。动态条件仍由后端的 supports/validate 函数检查。

注册表适合消除重复声明，不适合塞入所有物理逻辑。TeNPy、torch 和 PEPS 的内部结构不用强行一致；实验协议与特定论文模型应留在模型/应用模块，不能继续积累到通用路由中。

## 渐进整理顺序与验收

1. **先修物理与执行错误**：缓存键、位序/标签、初态分支、适用域检查、漏分派与漏转发；每个问题先加最小回归。
2. **统一能力与配置入口**：规范默认值和不支持行为，清理已弃用参数；schema 宣称的每个后端都走一次 build→evolve。
3. **统一 Basis 与结果元信息**：保持旧字段兼容适配一段时间，GUI/Web/摘要逐步迁移；不要求一次改变所有消费者。
4. **统一资源边界与物理编译输入**：去掉无条件稠密化，减少公共公式重复，保留独立性能实现。
5. **最后清理结构**：缩短路由分支，删除死代码，更新当前能力文档；避免只移动文件但保留重复事实源。

回归应覆盖不对称原子参数、复驱动、非平凡初态、分段跳变、投影与固定荷。对称全 g 初态容易掩盖原子顺序反转。还要检验错误组合被拒绝、实际使用参数与请求一致、未计算量不会变成零。
