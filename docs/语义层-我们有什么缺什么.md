# 「语义层」是什么 · Re0 有吗（2026-09-18）

> 使用者问：「"语义层"是什么意思，对应到我们当前 Re0 项目，我们有语义层吗？」

---

## 一、这个词有四种常见意思

| # | 领域 | 指什么 | 目的 |
|---|---|---|---|
| **1** | **数据 / BI**（dbt、Cube、LookML） | 在原始表之上定义**业务实体与指标**，让所有人查 `revenue` 而不是 `sum(price*qty)` | **一个指标只有一个定义** |
| **2** | **编译器** | 解析（语法）之后的阶段：符号表、名字解析、类型检查 | 管**意义**，不管写法 |
| **3** | **知识图谱 / 本体**（RDF/OWL） | 术语的形式化定义，让机器能推理 | 机器可读的**共识** |
| **4** | **AI / Agent** | 给模型的**有意义的操作与命名**（工具面、术语表），而不是原始内部结构 | 模型不必猜内部 |

**共同点只有一条**：
> **把"数字 / 字符串"变成"有意义的东西"，并且让这个意义只有一处定义。**

第 4 种是我们最该关心的——因为 Re0 有 AI 面。

---

## 二、Re0 现在有 6 块语义碎片

| 碎片 | 在哪 | 它赋予什么意义 |
|---|---|---|
| **单位约定** | `evolve_util.CONV = 2π·1e-3`；`runspec.py:27` 的 `## 单位` 段；`evolve_twofield.py:22`、`field_build.py:114`、`evolve_rwa.py:597`、`evolve_util.py:7` 各自再写一遍 | 裸数字 → 物理量 |
| **态身份键** | `atomic_levels.state_key` = `(kind,n,l,j,m,E)` + `find_state_index` 三级回退 | "第 7 个态" → "60S₁/₂ m_J=+0.5" |
| **登记册键** | `groups.list` / `field.B_gauss` / `dynamic.*` / `solve.*` | 配置 → 有名字的字段 |
| **结果自描述** | `res['states']`（第 1 刀统一） | 布居第 k 列 → 哪个态 |
| **两个名字** | `auto_label`（身份名）+ `group_label`（人工名，第 12 刀） | 机器认的名 vs 人认的名 |
| **AI 工具面** | `src/ai/server.py` 的 **43 个 MCP 工具**（`list_levels` / `set_initial_state` / `run_compute` / `get_diag` / `list_params` …） | 引擎内部 → 有意义的操作 |

**⇒ 合起来，这已经是一层语义层了。** 只是——

**它没有名字、没有单一定义点、没有判据守。**

---

## 三、缺的不是"一层"，是"单一定义点"

同一个"意义"现在散在多处，而**消费者有三个**：

| 消费者 | 走哪条路 | 依赖 |
|---|---|---|
| **GUI 参数页**（上帝模式） | `solver_inspector.py`（**9 处** `from ..core import params`） | `core.params.SPECS` |
| **AI `list_params`** | `server.py` → `sim_state.schema()` → **`pm_setup`**（`god_read`/`god_write` 用 `_P.DEFAULTS`） | `core.params.DEFAULTS` |
| **离线扫描** | `runspec.build_run` | `SOLVE_KWARG` |

**⇒ 参数那一刀（第 11 刀）断的不只是 GUI 参数页，还有 AI 的 `list_params`**——
AI 面不直接 import `core.params`（`server.py` 里没有），但**经 `pm_setup` 传递依赖**。
**这一点先前没写清。**

### 三处具体的"意义重复"

1. **单位**：`CONV` 单源了 ✓，但「B=Gauss、E=V/cm、t=ns…」这句话在 **5+ 个 docstring 里各写一遍**。
   **没有机器可读的单位表。**
2. **参数的元数据**（label/unit/range/desc）：值就地定义了（第 11 刀）✓，**元数据没有家**
   ——`pm_setup` 从 `core.params.SPECS` 取，而那个文件**已删**。
3. **`solve.*` 的映射**：`runspec.SOLVE_KWARG` 与 `pm_setup._SOLVE_SPECS`
   （5 元组，末列是 kwarg）**两份平行声明**。

---

## 四、所以：Re0 有语义层吗

**有事实上的语义层；但没有把它当一层来管。**

- **有没有**：**有**——单位约定、身份键、结果自描述、AI 工具面，都是语义层该干的事
- **是不是"一层"**：**不是**——分散、无名、无单一真源、无判据
- **该不该建**：**该，但要克制**

**真正的需求只有两条**：

1. **同一意义只有一处定义**（单位表 / 参数元数据 / `solve.*` 映射）
2. **消费者能查到它**（GUI、AI、扫描**共用一个查询口**）

**⇒ 第 11 刀留下的那个洞（"元数据搬不走，UI 需要一张全表"）就是这条需求的直接体现。**
「那张表住哪」——**这就是语义层问题**。

---

## 五、对迁移工单的影响（**改写了 C1**）

原 C1：「**引擎参数页**怎么办？」

**新 C1**：「**参数语义的单一查询口**放哪？」

因为现在有三个消费者要同一份东西：

```
GUI 参数页 ─┐
AI list_params ─┼─→ 需要：每个参数的名字 / 类型 / 单位 / 范围 / 说明 / 默认值
离线扫描 ─┘        + 它对应哪个引擎形参（solve.* 的映射）
```

**一个可能的落点**（不急着定）：把"元数据"与"值"分开——

- **值**：就地定义在各引擎模块（第 11 刀已做）✓
- **元数据**：一张**可查询的表**，由引擎侧声明、由消费方收集
  （`src/ui`/`src/ai` 本来就 import 全部引擎，收集器放消费方不会成环）

**关键约束**：`src/core` 内部**不能反向 import 消费方**（会成环）——
第 11 刀 `params.py` 的"零依赖"就是这个约束的产物。

---

## 六、一句话总结

> **Re0 有一层事实上的语义层（单位 / 身份键 / 结果自描述 / AI 工具面），
> 但它没有名字、没有单一真源、没有判据。**
>
> **缺的不是"加一层抽象"，而是"让同一个意义只有一处定义，并让三个消费者查得到"。**
