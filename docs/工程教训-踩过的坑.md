## 1. numba `@njit` 函数里的报错文案**不能带格式化**

- **发现经过**：物理同事在 `src/core/dop853.py` 的步长下溢分支写了一句友好的报错
  （用 `%` 插入具体数值），结果**所有 numba 引擎编译失败**，编译期报：
  ```
  No implementation of function mod for (unicode_type, UniTuple)
  ```
- **根因**：numba nopython 模式**不支持元组 `%`-格式化**（字符串格式化在 nopython 下支持极有限）。
- **现在的做法**（`dop853.py:365-371`）：报错用**静态串**，并把"下限值见 `_H_ABS_MIN`（1e-12 ns），
  改一处要同步这句文案"写进注释——因为 `njit` 里**没法自动把值拼进消息**。
- **纪律**：在 `hard.py` / `coupling.py` / `dop853.py` 等被 `@njit` 编译的函数里，
  **任何 raise 的消息都必须是字面量**；要带数值就分两层（njit 内抛固定串、外层 catch 后再补细节）。
- **为什么值得记**：它**不是运行时错误，是编译期错误**，且报错指向 numba 内部（`UniTuple`），
  很难一眼联系到"我在 f-string 里带了个值"。

## 2. 判据要「**报告变化**」，不要「**因为变化而变红**」

- **发现经过**：`checks/mecha_kernel_selfcheck.py` 原先断言
  `len(engine_params) == len(GOLDEN)`（总数相等）。物理同事每新增一个内部 `Param` 都会把它弄红——
  两人都在跑，就互相打断。
- **现状**：改成了**漂移侦测**——`GOLDEN` 里的项**缺失/值变 → FAIL**；
  **出现新参数 → `[note]` 列出**（要求登记，但不判红）。致死性也实测了
  （改名→2/6 红、改值→1/6 红、**仅新增→0 不误报**）。
- **纪律**：判据的使命是**把变化暴露给人**。若一条判据会被"别人合法的改动"弄红，
  它就会训练人忽略红色——那比没有判据更糟（D4：假绿比红更危险，假红同样有害）。

## 3. 写路径的**反方向**也要守：`I6` 只查了一半

- **证据**：`src/core/protocol.py` 的 `runspec_read_keys()` docstring 自述
  "I6：这些键都须在 config_schema（防漂）"——它 AST 扫 `runspec.py` + `manybody/runspec_mb.py`
  对快照的**读取**，断言"读的键都在 schema 里"。
- **缺的那一半**：**schema 声明了、却没人读**的键**无人守**。这正是
  `manybody.template` / `energy_window_mhz` / `manybody.seed` 三个键"声明了但无效"能溜过去的原因。
- **纪律**：契约守卫要**双向**。建议断言"schema 里每个键要么被实读、要么在**显式白名单**里"——
  一条判据就能抓住这类"声明了没接线"的键。
- **状态**：已作为建议交给机甲同事（并入 P0-6）。

## 4. 同一参数名在不同服务里**语义不同**（`--root`）

- **证据**：`src/adapter/serve.py:95` 的 `--root` 要**项目根**（内部拼 `.mecha`）；
  `cockpit.server.create_app` 是 `root = root or _default_root()` ⇒ **原样使用**，要 **journal 目录本身**。
- **实测**：`--root <repo>` → `GET /` 200 但 `/api/history` **count:0**；
  `--root <repo>/.mecha` → **count:247**（与盘上 247 行逐数一致）。
- **为什么危险**：**传错不报错**——页面正常 200，只是**永远看不见事件**（假绿）。
- **处置**：**不改语义**（该用法已出现在 dsh 插件/文档，改则破坏），改为**三处文案**消除坑：
  `--help`、启动打印（明确打印"journal 目录 = <最终使用的路径>"）、以及
  `_default_root()` 的报错（**原文案本身就在教人踩坑**：它让人"给 `--root <项目根>`"）。
- **纪律**：**跨服务同名的参数，必须在 `--help` 与启动日志里写清"它要的是哪一种路径"**；
  更根本的是——**传错的后果不能是静默**。

## 5. `max_step` 这类"看起来像上限"的参数，其实只是**起步提示**

- **证据**：`src/core/dop853.py:239-243` 的 docstring 自述 `max_step` 只在**起步**参与
  `h_abs = min(100·h0, h1, interval, max_step)`，之后按误差控制自由增长
  （自附实测：请求 0.05 ns 的 10 ns 演化里出现 **2.2 ns** 的接受步）。
- **后果（C1b 事故）**：窄脉冲下包络在脉冲外**恰为 0** ⇒ 误差估计看到 **0 误差** ⇒
  步长涨到 ~60 ns ⇒ **整个脉冲被一步跨过**（σ=2 ns 时给 7.7e-94，而解析是 2.48e-4）。
- **纪律**：调一个"限步长"的参数**不等于**限住了步长。要真压步长得用
  `solve.MAX_STEP_HARD`（每个接受步都复核的硬上限）。**自适应步长对"零误差区间"的反应是合理的**——
  错的是"零误差"这个信号本身（包络真值为 0），所以要靠**包络特征时长**而不是容差去救。
- **附带**：`MAX_STEP_HARD` 调小到某些值会**连续拒绝把步长压到 0** ⇒ 稠密输出抛
  `ZeroDivisionError`（反直觉："调小反而必崩"）。现已改为可教学报错。

## 6. 共用工作区里的 git 纪律（主代理亲自踩过两次）

- **踩过什么**：`git add -- <我的文件>` 之后紧接 `git commit`，**会把同事已暂存但未提交的文件一起卷走**
  （`git commit` 不带 pathspec 时提交**整个暂存区**）。
- **还踩过一次更糟的**：为拆提交用了硬回退，**把自己三个已提交的工作变成孤儿**
  （文件还在磁盘但掉出历史；靠 `git reflog` 找回）。
- **纪律**：
  1. **只用 `git commit -- <明确路径>`**（pathspec 会限制提交范围）；
  2. **禁止** `git add -A` / `git add .` / `git commit -a`；
  3. 提交前先 `git status --porcelain` 看**整个暂存区**，不只看自己 add 的那几个；
  4. 拆提交用 `git restore --staged`，**不要**用硬回退；
  5. **一条任务一提交**——攒着改动的代价是"一次中断就留下无法判断的中间态"
     （实测：某同事崩溃时工作区积了 **17 文件 / 769 行**未提交）。

## 7. 崩溃/中断后的恢复纪律（本会话踩了三次）

- **先验树、再唤醒、别重做**：
  1. **验树**：改动文件是否语法有效 + 关键模块能否 import + 跑最内圈判据（`--core`，33s）；
  2. **唤醒同一个 agent**（保留其模块上下文，比重起更省），并附"别重做、按序恢复"的指令；
  3. **要求它先报状态**：哪几条做到哪一步、哪几处**未验证**（半成品最危险）；
  4. 若上下文已丢，给**完整交接简报**，不要让它重新探索。
- **为什么**：崩溃本身不致命，**"崩溃留下的未验证半成品"才致命**——它会让下一个人以为那部分已完成。

## 8. **"我的模型对不对"必须用实测回答，不能靠推理**（本会话纠正了三次）

- **案例**：主代理先后三次给出**听起来合理但实际错误**的判断，每次都由同事**先测再改**而发现：
  1. 我说"驾驶舱的 `--root` 传项目根"——错。它**原样使用**，传项目根会静默 `count:0`
     （照做了就会埋一个假绿进启动器）。
  2. 我说"没人读 = `runspec` 不读"——错。`field.n_photon`/`field.window` 走的是
     **另一条消费路径**（`src/ui/fields.py:278` 的 `br.read(...)`）。照"只扫 runspec"写守卫，
     会把两个**正当键误判成死键**。
  3. 我推断"`DIRECT_SOS_N_WINDOW` 可以复用为配置键"（在给同事的指令里）——错。它 `family='engine'`，
     写入被拒（同事实测后改用自己的两处声明）。
- **纪律**：给同事的**施工指令里，凡是"我认为 X 是这样"的部分，都要标明可信度**，
  并要求"先验证再照做"；同事若发现前提错，**要拒绝照做并纠正**——本会话正是这样避免了三次返工。
- **反面**：如果同事"照指令执行"，这三次都会变成**写进代码的静默错误**，而且都在"看起来对"的地方
  （启动器能起、守卫能绿、键能声明）。
- **一句话**：**在这个项目里，"我读过代码了"不等于"我知道它怎么跑"**——尤其涉及
  「路径语义 / 消费路径 / 家族权限」这三类时，必须实测。

## 9. 「靠类型名触发的分派」是**静默失效**的高发区

- **场景**（2026-09-22，P2-2 落地时发现）：库的 `registry.validate` 是否委托 `engine.validate_custom`，
  取决于**该键的 `type` 是否命中 `engine.custom_types()`**。于是适配器为了保护
  `manybody.drive_segments`（core 里声明为通用 `type='list'`），做了一处**类型改判**：
  `if _ds.get('type') == 'list': _ds['type'] = 'drive_segments'`。
- **脆弱点**：这条保护链有四个环节——`schema 的 type == 'list'` → 适配器改判 → `custom_types()` 含它
  → `validate_custom` 有分支。**任何一环静默变化，结构校验就无声消失**：
  例如物理侧哪天把那个 `type` 从 `'list'` 改成别的，改判条件不满足 ⇒ **不报错、不告警、校验没了**。
  而当时的守卫只查"`custom_types()` 声明的类型是否真实现了 `validate_custom`"，
  **不查"它是否真的被某个键用上"**。
- **纪律**：**凡"靠名字匹配来决定是否分派"的接法，都要一条反向断言**——
  「声明的分派目标，必须真的被某个输入用上；输入若改名/改类型，必须变红」。
  否则你得到的是一个**看起来在保护、实际已断开**的机制（与 I6 的"哑告警"同族）。
- **推广**：同族风险还有——注册表按类型名分派、插件按协议名注册、告警按 `kind` 字符串匹配、
  CodeAct 按动词名注入归因。**共同点：名字是字符串，改名没有类型检查兜底。**

## 10. 跨键约束与单键约束要**分开安置**

- **场景**：`manybody.drive_segments` 的真契约含两类条件——**结构**（是 list、非空、元素是 dict、
  有 `t0`、`t0>=0`、`Om` 是序列）与**跨键**（`Om`/`delta` 长度 == 原子数）。
- **实测约束**：`registry.validate(key, value)` **拿不到快照**，所以它**做不到**跨键校验。
- **正确分工**（本次采用并写进注释）：**结构校验放在 `set` 当场**（早失败、可教学）；
  **跨键约束留在 `build` 阶段**（那里已有 `n_atoms=n`）。两者**共用同一个校验函数**
  （`validate_drive_segments(..., n_atoms=None)` 用参数区分），所以没有第二处定义。
- **纪律**：不要因为"要在 `set` 当场拒"就把跨键校验硬塞进单键校验器（它没有上下文，
  只能猜或放过）；也不要因为"`set` 做不到"就把结构校验也推到 build（那就晚失败）。
  **把能做的做早，做不了的明确留在有上下文的地方，并写明为什么。**
