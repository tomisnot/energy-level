# 静态页与动态页：能级组共用 & 频移引擎的甄别（2026-09-18）

> 问题（使用者）：① 从设计之初就认为**静态页和动态页的能级组部分是共用的**，
> 不知道后来执行成了什么样，总之**理应共用**；② 静态页计算频移的引擎
> **会不会在动态页中有所应用**——曾经有算法是应用的，但现在可能都不应用了。
>
> 本文用**源码 + 实测数字**回答这两问。沙盒 `D:\desktop\Re0重构`，
> 探针 `_probe_static_vs_dynamic.py`（可复跑）。

---

## 结论摘要（先看这个）

| 问 | 答 |
|---|---|
| ① 能级组部分共用了吗？ | **枚举原语共用了，但"枚举"这件事本身是两份实现。** 两页都调 `get_hyperfine_levels` / `trim_of` / `sublevel_trim`，但**各自写了一遍"组 → 子能级"的循环**，且**能量算法不同**（静态自算 Zeeman，动态调 `_sublevel_energy`）。实测**态集合完全相同**（好事），**label 与能量则不同**（见 §4）。 |
| ② 频移引擎在动态页应用了吗？ | **代码通路在，但生产路径已经断了。** 静态页的频移引擎 `direct_ac_stark_shifts` **确实**被动态侧调用（`field_build._floquet_ac_static` → `real_field` → `M = A + diag(ac)`，位移**真进哈密顿量**）；**但 `real_field` 在生产代码里零调用**——唯一外部调用者是 `checks/mw_bench_firstprinciples.py`（一个 `--slow` 才跑的基准）。产品改用 `build_fields_exact`，其 docstring 明写「**不注入任何静态能移**」。**⇒ 你的判断成立：曾经应用，现在不应用了。** |

**一句话**：`direct_ac_stark_shifts` 现在**只服务静态页显示**；面板上控制它精度的
`n_photon` / `sos_n_window` 两个控件，**对任何生产演化都不再有影响**——
而 `static_atom.set_ac_stark_config` 的 docstring 还写着「静态页与动态页统一受控」。

## 1. 静态页的路径（源码级）

```
ui_single.py:119  rows = core.build_level_rows(cache, field_B, groups, address_cfg, visible)
                       └─ static_atom.build_level_rows          (L839-846)
                            └─ build_level_rows_direct          (L903-910)
                                 ├─ rows   = _base_level_rows(...)          (L849-891)  ← 组 → 子能级行
                                 │            ├─ get_hyperfine_levels(cache,n,l,j,B)   ← 低激发态展开 (F,m_F)
                                 │            ├─ cache.gJ(l,j) + MU_B_MHZ_PER_G        ← **自己算 Zeeman**
                                 │            └─ apply_trim(...)                       ← 逐子能级裁剪
                                 └─ shifts = direct_ac_stark_shifts(cache, groups,
                                                                    address_cfg, field_B)  ← **频移引擎**
ui_single.py:540/546  lines = core.spectrum_lines(cache, rows, ac_on=...)      (L1064)
```

**关键**：静态页的能级 = 组中心 `cache.E_mhz` + **自算 Zeeman** + **AC 位移**。
**没有 DC Stark。**

## 2. 动态页的路径（源码级）

```
runspec.build_run(p)  →  build_states(cache, groups, B_gauss, E_vpcm)      (L79-122)
                             ├─ core.trim_of(g) + core.sublevel_trim(ms, Fs)   ← 裁剪（与静态页同一对函数）
                             ├─ core.get_hyperfine_levels(cache,n,l,j,B)       ← 同一原语 ✓
                             ├─ core._sublevel_energy(cache,n,l,j,m,B)         ← **能量用这个**（不是自算 Zeeman）
                             ├─ core.dc_stark_shift_mhz(...)                   ← **额外加 DC Stark**
                             └─ make_levels(cache, specs)   (atomic_levels.py:40-71)
                                     └─ label = core.auto_label(n,l,j) + ' m_J=…'
```

**关键**：动态基组的能级 = 组中心 + `_sublevel_energy` + **DC Stark**。
**没有 AC 位移。**

## 3. 频移引擎的甄别：`real_field` 这条线

### 3.1 代码通路（曾经是通的）

```
static_atom.direct_ac_stark_shifts          ← 静态页的频移引擎
     ├─ 静态页：build_level_rows_direct 直接调（**活**）
     └─ 动态侧：field_build._floquet_ac_static            (L29-69)
                    ↓ docstring 原文：
                    「用**静态页同款 Floquet 引擎**（core.direct_ac_stark_shifts）
                      计算**动态 states** 每个能级的 AC 位移」
                field_build.real_field                    (L321-435)
                    ↓ L415  ac = _floquet_ac_static(...)
                    ↓ L428  M = A + np.diag(ac)           ← **AC 位移进哈密顿量**
                    ↓ L421  失败时回退 far_sos 版
```

`static_atom.set_ac_stark_config` 的 docstring（L521-527）把这个共享写得很明白：

> 供静态页面板控件调用；`direct_ac_stark_shifts` / `direct_ac_stark_sweep`
> 在参数缺省（None）时读取此配置 → **静态页与动态页（`real_field` 经
> `_floquet_ac_static`）统一受控**。

### 3.2 但这条路现在断了（AST 全仓调用点搜索）

`real_field(` 的**真实调用点**（排除归档，沙盒 + 正式仓）：

| 位置 | 性质 |
|---|---|
| `src/core/field_build.py:421` | **它自己的内部回退**（递归，`B_gauss=None`） |
| `checks/mw_bench_firstprinciples.py:262, 284, 290` | **一个判据**（`--slow` 才跑，18 分钟） |

**⇒ 生产代码零调用。** 同批的 `field()`（L292-300，9 行）与 `group_field()`
（L305-316，12 行）也一样——调用者**全是判据**（`evolve_dissipative_selfcheck` /
`evolve_exact_selfcheck` / `pair_evolve_selfcheck`）。

**产品路径走的是另一支**：

```
runspec.build_fields_single/pair  →  field_build.build_fields_exact   (L148-206)
     docstring 原文：「…**全部**偶极允许对都进耦合矩阵——远失谐对的效应由
     精确传播自动给出，不存在近/远分流边界，也**不注入任何静态能移**。」
```

**而且 `evolve_rwa`（唯一接受 `real_field` 输出的引擎）也已经不在产品面上**——
`src/ui/ui_dynamic.py:292` 的注释：

> `# 引擎层仍可用（evolve_rwa ip4 / route_auto 脚本调用），GUI 不再暴露；`

## 4. 实测：两页到底差多少（探针数字）

配置：`B=21.7 G`，组 `60S1/2 + 60P3/2`，寻址光 `295.7 THz / σ- / 1e4 mW/cm²`。

### ① 静态页：AC 位移随寻址光变化（最高 **+4988 MHz**）

| (n,l,j,qstr) | E 光关 (MHz) | E 光开 (MHz) | Δ |
|---|---:|---:|---:|
| 60,0,0.5, `m_J=-0.5` | -1017273.4046 | -1017027.0387 | **+246.37** |
| 60,0,0.5, `m_J=+0.5` | -1017212.5904 | -1016964.7440 | **+247.85** |
| 60,1,1.5, `m_J=-1.5` | -1000016.3663 | -1003612.3838 | **−3596.02** |
| 60,1,1.5, `m_J=-0.5` | -999975.8472 | -999716.6463 | **+259.20** |
| 60,1,1.5, `m_J=+0.5` | -999935.3280 | -999704.5098 | **+230.82** |
| 60,1,1.5, `m_J=+1.5` | -999894.8089 | -994906.3751 | **+4988.43** |

### ② 动态基组：**对寻址光完全无感**

| (n,l,j,kind) | E (MHz) | 对应静态页"光开"值的差 |
|---|---:|---:|
| 60,0,0.5,mJ | -1017273.4046 | **246.37 MHz** |
| 60,1,1.5,mJ | -999894.8089 | **4988.43 MHz** |

（动态基组的值 = 静态页**光关**列。⇒ AC 位移**一个 MHz 都没进**动态基组。）

### ③ 态集合：**完全相同**（好消息）

```
静态 rows : 6 个      动态 states: 6 个      完全相同: True
```

`(n,l,j,m)` 一一对应——**枚举口径是对齐的**（这正是 2026-09-14 那次
"能级组是两页共同区域，必须一致"裁决的成果）。

### ④ label：**同名不同字**

```
静态 rows   的 label: ['60S', '60S', '60P', '60P', '60P', '60P']        ← 能级组的人工 label
动态 states 的 label: ['60S_{1/2} m_J=-0.5', …, '60P_{3/2} m_J=+1.5']   ← auto_label 自生成
能级组人工 label 是否被动态页采用: False
```

⇒ **实证了"两页同名不同字"**：静态页用你在能级组里起的名字，动态页用
`auto_label` 拼的名字。

## 5. 判断：哪些是设计，哪些是债

| 现象 | 是设计还是债？ |
|---|---|
| 态集合一致 | **设计**（2026-09-14 裁决的成果，`apply_trim` 就是为它加的） |
| 动态基组不含 AC 位移 | **设计，而且物理上更对**：光移应由光场耦合在传播中**涌现**，不当初始能偏注入（`build_fields_exact` 的"精确传播自动给出"） |
| 静态页不含 DC Stark | **债**：动态页加了 `dc_stark_shift_mhz`，静态页没加——同样的 `E_vpcm` 下两页能量会分叉。**已用全仓 AST 调用点搜索坐实**：`dc_stark_shift_mhz` 的调用点只有 `src/core/runspec.py:113,124`（动态路径）；静态页的 `_base_level_rows`（L849-891）**一次都不调它**。 |
| label 不同字 | **债**：同一批子能级在两页显示成两个名字；当年靠 `_retag`（适配层）钉，说明确实疼 |
| 能量算法两份（`_sublevel_energy` vs 自算 Zeeman） | **债**：同一个量两处实现，漂移风险 |
| `set_ac_stark_config` 声称"静态页与动态页统一受控" | **债（文档与实态不符）**：动态侧唯一通路已死 |
| 面板 `n_photon`/`sos_n_window` 控件 | **债**：现在只影响静态页显示，不影响任何生产演化——但界面没说 |
| `real_field` / `field` / `group_field` 三个遗留场构造器 | **死代码**（生产零调用，只有判据和 1 个基准在用） |

## 6. 重建建议（按"你的设计意图"归位）

**你从设计之初的意图是对的**：能级组是两页的共同区域。执行偏成了
"两套实现 + 分别对齐"。重建时应做的是**一处实现**：

1. **收成唯一的"组 → 子能级"函数**，签名只依赖 `(cache, groups, B, E_vpcm)`，
   返回**带完整身份**的中间结构（`(n,l,j,kind,m/F,amps,E_base)`）。
   - 静态页要的 `x / color / qstr / ac` 由这层**投影**出来；
   - 动态页要的 `make_levels` 输入由这层**投影**出来。
   - ⇒ 能量算法只剩**一份**（选 `_sublevel_energy`，它与静态页自算 Zeeman 是否等价**需要先对拍**）。
2. **DC Stark 的归属要拍板**：要么两页都加，要么都不加，要么明确"只有动态加，因为
   静态页显示的是**无静电场**的能级"。**必须写进文档并在界面上可见**。
3. **label 统一**：让动态页也认能级组的人工 label（或让两页都走 `auto_label` +
   显示层叠加人工名）。**不要在适配层里 `_retag`**——那是治表。
4. **AC 位移的定位要写清**：它是**静态显示量**（"这个光强下各能级移多少"），
   **不是**演化初值。若要让它影响演化，用 `real_field` 那条注入路径——
   但那与"精确传播涌现"是**两种物理近似**，**不能同时开**。要么二选一，
   要么在界面上明确它们是两个不同的模型。
5. **删或明确三个遗留场构造器**（`real_field` / `field` / `group_field`）：
   如果要保留 `real_field` 作为"注入静态能移"的模型，它必须**重新接进产品路径**
   （现在断了）；如果不保留，它就是死代码，连同 `set_ac_stark_config` 那句
   "动态页统一受控"的承诺一起清掉。

**下一刀的建议**：先做 **1（唯一枚举函数）** 和 **3（label 统一）**——
它们直接对应你的原始设计意图，且**可判据化**（态集合 + 能量 + label 三项对拍）。
第 2 和第 4 条是**物理裁决**，得你拍板。
