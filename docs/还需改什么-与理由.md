## 3. 参数白名单靠手抄（最划算的一处）

### 现状

```
SOLVE_KWARG        solve.* → kwarg 映射（手抄，注释说"必须与 pm_setup._SOLVE_SPECS 一致"）
god_kwargs_from_params   全量收 solve.*/engine.*
_filter_kw(d, allow)     按白名单筛；allow 来自
    _MIXED_PAIR_KW / _MIXED_SINGLE_KW / _HARD_KW   ← **照引擎签名手抄**
```

三层里**两层是手抄的**。我第 2 刀加的 `_HARD_KW` 就是这么加的。

### 为什么要改

**手抄表的失效方式是静默的**：引擎加/改一个参数，白名单不会自动跟上，
症状就是"设了参数却没生效"——**`max_step_hard` 那个洞就是这么来的**：

> `SOLVE_KWARG` 里**已经**有 `'MAX_STEP_HARD': 'max_step_hard'`，参数一路收上来，
> 却在最后一跳被整包丢掉；旧文案只好写"请经库 API 直调 `hard.evolve_hard`"。

### 怎么改（很直接）

`_filter_kw` 用 `inspect.signature(引擎函数).parameters` 派生白名单：

```python
def _engine_kwargs(fn, d):
    """按**引擎签名**筛 kwargs——白名单即签名本身，不是手抄表。"""
    allow = set(inspect.signature(fn).parameters)
    return {k: v for k, v in d.items() if k in allow}, {k for k in d if k not in allow}
```

收益：**白名单从"手抄表"变成"签名本身"**，引擎改签名，筛子自动跟。
`_MIXED_*_KW` / `_HARD_KW` 三个常量可以删掉。

### 验收

故意往 RunSpec 里塞一个引擎不认的键 → **构建期**写进 `warnings`（当前行为），
且塞一个引擎**认**的键 → 一定到达引擎（可用 `inspect` 断言）。

## 4. 两页 label 仍不同字（第 4 刀没修）

### 实测

```
静态 rows 的 label: ['60P', '60S']                                 ← 能级组的人工 label
动态 states 的 label: ['60P_{3/2} m_J=+0.5', …, '60S_{1/2} m_J=-0.5']  ← auto_label 自生成
```

第 4 刀统一了**态集合与能量**（逐位一致 ✓），但 **label 没统一**——
`base_sublevels` 把组的 `label` 带给了静态页，而 `make_levels` 自己生成另一个。

### 为什么要改

用户在静态页看到的是**自己起的名字**，在布居图/动态页/AI 回执里看到的是**自生成的名字**。
**同一个态两个名字**——查一个布居峰要来回对，且两体的成对标签更是人工 label 拼的
（`(60S) x (60P)`）。

### 两个方案（要你选，见 §8）

- **A. 动态页认人工 label**：用户看到自己起的名字；但两体/叠加态下人工名可能不唯一，
  需要定"重复名怎么办"。
- **B. 两页都走 `auto_label`，显示层再叠加人工名**：物理身份清晰、显示灵活；
  但用户"起的名字"不再出现在数据里，只能出现在界面上。

## 5. `method='sambe'` + 有耗散 → 实际跑的是 `evolve_reference`

### 证据

`sambe.py` 的 `evolve_sambe` docstring：

> `decays : 非空 → 转 evolve_reference（Lindblad，第一期执行路径）`

而 `evolve_sambe` 里确实有一条 `return evolve_reference(...)`（走 Lindblad）。
技能文档也确认：「单原子 + `sambe` 遇通道会转入 **Lindblad 主方程**（`backend=reference-bdf`），
是 GUI 上唯一能跑显式落点/纯退相的组合」。

### 为什么要改

**`RunSpec['method']` 说 sambe，`res['backend']` 说 `reference-bdf`。**
后果：

- 用 `method` 做判断的人（GUI 的方法显示、扫描轴、AI 的提示词、"哪个引擎跑的"日志）
  **会得到错信息**；
- 用户以为自己选了 Sambe（免 RWA 精确），实际跑的是参考积分器——**这是有物理含义的差别**，
  不该静默改道。

**改法**：要么在 `RunSpec` 里显式记 `method_in` → `method_used`（已有 `method_in` 字段！
可利用），要么把改道写成 `warnings` 让用户看见。**核心是"执行的东西要能被看见"**。

## 9. `params.override` 全局栈【I】

`params.py` 是全局注册表 + `override(values)` 上下文管理器，`effective()` 读**栈顶**。
`runspec.evolve_run` 用 `with _P.override(ovr):` 包住引擎调用。

**为什么是问题**：并行扫描是**多进程**（每进程独立栈）所以现在没事；但
**线程内嵌套调用**、**同一进程里跑两次不同配置**都靠约定。参数不是显式传递的，
阅读代码时看不出"这个引擎用的是哪套参数"。

**改法**：把运行级参数显式传（`RunOptions`），`override` 只留给 GUI 的临时试验。
**优先级不高**（当前架构是多进程），但它是"参数从哪来"这个问题的根。
