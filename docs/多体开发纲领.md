# 多体开发纲领

> 长期文档，管方向与取舍，不追具体实现细节。
> 与代码冲突时以**代码 + 运行结果**为准；本文件随共识演进，变更记在文末。
> 适用面：`src/core/manybody/`、多体相关的 `mecha_v2/`、`checks/`、文档与脚本。
> **单体/两体引擎已冻结**：除修复明确 bug 或共享层被动受益外，不再主动开发。

---

## 1. 三个目标

### 1.1 正确性：结果必须能被独立复现

正确不是"测试多"，而是四件事同时成立：

1. **语义明确**：基序、原子顺序、单位、边界、近似条件都写在契约里，不靠猜。
2. **独立可复现**：关键结果至少有一个**不同实现路径**能对上（解析解、独立稠密装配、
   跨后端、上游独立脚本）。
3. **不变量可查**：厄米性、范数、电荷守恒、能量漂移、Ritz 残差、置换权重等，
   在运行时就能被检查，而不是只在测试里。
4. **边界会拒绝**：不支持就报错并给替代；绝不静默给另一个问题的数值。

证据强度从高到低：

```
解析闭式 > 独立实现逐位对拍 > 跨后端同模型对拍 > 收敛性/不变量 > 单元断言
```

新能力的最低证据包：**一个精确小系统 + 一个拒绝案例 + 一个运行时不变量**。三者缺一不做。

### 1.2 简洁：概念少，而不是行数少

简洁的本质是**概念压缩**：

- **一个概念只有一处定义**。同一物理量、同一基序、同一能力，不允许第二份手抄。
- **声明优先于镜像**。能由 schema/能力表/签名派生的（GUI 选项、错误文案、测试矩阵），
  不再手写一份。
- **派生优先于复制**。同一套项语义允许有不同的编译表示（CSR、LinearOperator、MPO、
  torch 张量），但"项是什么、符号怎么定、基怎么排"只能有一处。
- **删除优先于新增**。新分支让旧分支变成死代码，就删旧分支；不留兼容 shim。
- **新模块要有两个消费者，或替代一个旧模块**。否则它是悬空的，应该并入现有模块。

### 1.3 高效：优化共享核，而不是给单引擎打补丁

性能层级从高到低：

```
算法/近似 > 基与数据布局 > 算子核（matvec/收缩/测量） > 微优化（分配、dtype、循环）
```

纪律：

- **先测量，后优化**。没有基线数字的"优化"不接受。
- **共享核优先**。一个 matvec 快一次，ED、Lanczos、GPU、扫描全受益；单引擎特化越加越乱。
- **Python 循环是嫌疑犯**。循环遍历态、键、时刻、字符串时，先问能否用 numpy 掩码/
  索引表/批量矩阵乘替代。
- **预计算纯映射**。基索引、位翻转表、Pauli 相位、Schmidt 分割映射，凡是与时间无关的，
  不应在每个时刻重算。
- **内存有预算**。任何可能物化 `O(2^N)` 或 `O(n_t·dim)` 的路径，都要有预算、分块或拒绝。
- **保留参考路径**。快路径必须能与 reference/稠密小系统对拍；不许"快了但没人知道对不对"。

### 1.4 三者冲突时怎么裁决

1. **正确性一票否决**。任何"更快/更简"但改变物理语义或静默降级的方案，不进入产品路径。
2. **简洁与效率冲突**：优先"共享语义 + 多种编译表示"。语义只有一份，性能实现可以分叉，
   但每个分叉都要与同一份语义对拍。
3. **通用与专用冲突**：先问"这是不是某一类能力的一个实例"。
   - 是 → 先补类级能力（通用 Pauli 串、通用测量、通用通道表），再加实例；
   - 否 → 说明为什么现有类表达不了，并把它限制在模型/实验层，不进通用引擎。
4. **近似与精确冲突**：近似必须是**显式后端或显式开关**，并带误差指标与语义标注；
   禁止把近似结果塞进纯态字段而不标注。
5. **新增与简洁冲突**：不接受"为完成一个需求而造的悬空件"。
   任何新增都要回答：它属于哪一类？能否由现有声明派生？是否复用共享层？

## 2. 架构原则

### 2.1 分层与依赖方向

```
物理/数值  src/core/manybody/*        不 import Qt、不 import mecha
契约       schema_mb / backends / plan / results
适配       mecha_v2/*                 只做线程、Gate、任务、投影
视图       src/ui、web/run_monitor    只读快照与结果，不反向写物理
```

- `core ↛ mecha` 是硬约束；`mecha_v2` 只消费 `src.core.protocol`。
- 物理语义留在 core；框架不承载任何 Rb-87/EL 领域值。
- GUI 与 AI 走同一条 `build_run → evolve_run`，不允许 GUI 私有一条数值路径。

### 2.2 模型货币：`calib` 是唯一输入

- `manybody.calib`（atoms + pairs 的 V/J/A）是 RunSpec 唯一模型输入。
- 文件/ARC 只属于构造器（`el_build_calib`），不得出现在 RunSpec 里。
- 活跃通道由数值推导（V≠0→I1，J≠0→I2，A≠0→I3）；不设 `terms` 用户输入。
- 标定缓存键包含所有影响物理的字段（能级、位置、周期、项、B、窗口、截断），
  不包含 Ω/δ/Γ 等运行级驱动。

### 2.3 基与身份必须显式

- 位序：原子 0 是最高位（MSB），bit=1 ↔ `|r⟩`。
- 局部基：`|g⟩=0`、`|r⟩=1`；`σᶻ=diag(+1,−1)`、`σˣ=[[0,1],[1,0]]`、`σʸ=[[0,−i],[i,0]]`。
- 本仓 `sp/sm = |r⟩⟨g| / |g⟩⟨r|`，与教科书 σ± 编号相反；文档必须写这句。
- MPS 的 `order` 是"第 k 个 MPS 位置对应哪个原子"；对外观测量一律**原子原序**，
  内部按 `order` 映射，绝不混用。
- 任何新的基/投影/扇区，必须同时给出：编号规则、原子顺序、如何从全空间映射。

### 2.4 能力用声明，物理判断留在求解器

- `backends.py` 是后端能力的**声明表**：名称、别名、入口、任务、选项、是否支持
  分段/投影/耗散/返回态/荷/Pauli/观测/熵/关联/内部步长/近似语义。
- schema 枚举、GUI 选项、preview/estimate 的可行性、测试矩阵从这张表派生。
- **模型相关的适用条件**（是否守恒、是否 stoquastic、是否二次型、几何是否可排序）
  仍由求解器在 build/validate 阶段检查；注册表不塞物理逻辑。

### 2.5 测量与结果：一套语义，多种形态

- 公共观测量（占据、关联、熵、局部自旋、链路、环路、Pauli 串）只定义一次；
  后端只提供"每时刻的态/概率/系综"，不各自实现物理量。
- 近似后端（轨迹系综、经典因子化、PEPS 截断）必须标注 `approximation` 与误差；
  不得与纯态期望共用字段而不加语义。
- 结果契约先行：新后端先写 `data_schema`（quantity/axes/unit/identity/approximation），
  再写数值。
- 未计算的量不输出数值零；缺失用 `None`/NaN，并说明原因。
- `loss` 是兼容别名；新消费者区分 `physical_loss / norm_drift / no_jump_weight_deficit /
  survival_weight`。

### 2.6 资源、取消、状态

- 所有长循环消费协作取消标志；取消是请求，终态以结果为准。
- 内存/维度预算在**入口**检查，不在跑到一半时崩。
- 原生态（TeNPy MPS、torch 张量）与可展示数据分开；跨会话用 HDF5 checkpoint。
- 不隐式转换原生态（TeNPy ↔ torch）；需要时显式、可拒绝、说边界。

## 3. 新增能力的标准流程

任何新后端、新观测量、新配置键，按以下顺序走；不允许跳步直接写数值。

1. **归类**：它属于哪一类？现有类能否表达？不能表达时，缺的是类级能力还是模型特例？
2. **查重**：是否已有同义实现/第二份定义？有则合并，不新增。
3. **声明**：在能力表/schema 中加一行，写清支持面、选项、默认值与拒绝条件。
4. **共享层**：优先把通用部分放进测量/通道/基/结果层；后端只做适配。
5. **数值**：实现算法；保持纯函数、可取消、有预算。
6. **对拍**：精确小系统 + 独立实现/跨后端；记录数值与容差。
7. **拒绝面**：不支持的组合必须报错并给替代；错误文案点名参数与下一步。
8. **契约**：结果字段、形状、单位、语义标注、`data_schema` 一次写全。
9. **文档**：当前能力文档同步；临时需求文档并入正式文档后删除。
10. **基准**：记录机器、规模、耗时、内存；性能改动必须有前后对比。

### 3.1 四问准入

动手前先答：

1. 这是不是某一类的实例？能否用通用能力表达？
2. 能否由现有声明派生（schema/GUI/测试/错误文案），而不是再写一份？
3. 是否复用共享核？若必须特化，特化的边界在哪、如何对拍？
4. 是否有精确对拍 + 拒绝案例 + 运行时不变量？

四问答不全，就先做类级方案，或把需求退回模型/实验层。

## 4. 实现细则

### 4.1 性能

- 遍历态/键/时刻/字符串的 Python 循环，默认视为待优化点。
- 与时间无关的索引、掩码、相位、分割映射，预计算并缓存；缓存要有容量/内存上限。
- 避免在热路径里反复 `np.arange(dim)`、`flatnonzero`、`searchsorted`、`np.unique`；
  能用一次建表 + gather/index_add 的，不每步重算。
- 稀疏 vs 稠密：小维稠密 eigh 可以；大维一律稀疏/矩阵自由；任何无条件稠密化都要说明。
- GPU 路径：不静默回退 CPU；显存预算按"行 × 构型"估算并分块；dtype 策略显式。
- 近似算法：给出误差来源（截断、采样、步长）与收敛检查；不把"跑完"当"收敛"。

### 4.2 正确性

- 浮点比较用容差并说明来源；跨后端对拍优先用布居/能量/振幅重叠，不只比一个标量。
- 简并/近简并：先看 gap；单态期望在简并子空间不唯一，验收要劈开或说明。
- 实哈密顿量的本征态上，含奇数个 σʸ 的 Pauli 串期望恒为 0（时间反演），
  不能拿"全零"当通过。
- 任何"按守恒量切片/筛选"的入口，默认做一致性自检，允许显式关闭。
- 默认 `None` 必须逐位不变：不加新键时，数值、结果体积、`data_schema` 都不许变。

### 4.3 代码组织

- 先改现有模块，再考虑新模块；新模块必须有两个以上消费者或替代旧模块。
- 适配层薄：只做参数翻译、线程、错误归一；物理与算法在 core。
- 命名用物理量名，不用实验名/论文名（`chirality` 这类词留在调用方）。
- 注释解释"为什么"和"踩过的坑"，不复述代码；不写与实现矛盾的"唯一真源"。
- 删死代码、删过期注释、删临时文件；历史文档留在 `docs/history/`。

### 4.4 测试

- 用 `Checker.group` 组织**不变式包**，不把一件事拆成十几个碎片断言。
- 新后端/新观测量的判据必须：小规模、非对称、复耦合、非平凡初态；
  全 g 初态和对称点阵会掩盖顺序/符号错误。
- 共享基准基座（随机 calib + 精确稠密参考 + 不变量）优先于每个测试自带一套 setup。
- 无 CUDA/无 TeNPy 时诚实 SKIP，不伪造通过。
- 判据登记进 `run_checks.py` 的合适档位；默认 `--smoke`，共享层改动用
  `--cascade`（失败再展开 core）或 `--changed`。

### 4.5 文档

- 当前能力文档与历史文档分开；历史文档不追改。
- 临时需求文档的完成标志是**它消失**：内容并入正式文档后删除。
- `skills/energy-level/SKILL.md` 与 `.dsh/skills/energy-level/SKILL.md` 必须逐字节相同。
- 文档里的"支持面/拒绝面"表必须与能力表同源；不手抄第二份。

## 5. 验证体系

| 层 | 目的 | 例子 |
|---|---|---|
| 契约 | 声明与实现一致、拒绝面正确 | `manybody_contract`、`engine_contract` |
| 精确锚 | 小系统解析/独立实现 | `equibench_engine_ed`、`equibench_analytic_thermo` |
| 跨后端 | 同模型不同算法一致 | ED ↔ DMRG ↔ MPS ↔ GPU |
| 收敛 | 参数加密结果收敛 | χ、truncerr、max_step、Krylov 维 |
| 生命周期 | 线程、取消、存档、端口 | `gui_*`、`control_channel`、`run_monitor` |

性能基准协议：

- 固定机器、固定规模（如 N=12/16/20 的扇区基态、固定 χ 的 DMRG）、固定随机种子；
- 取 3 次中位数；同时记录峰值内存；
- 改动前后各一次，差异超过噪声才宣称收益；
- 正确性对拍与性能基准同一次提交，缺一不可。

### 5.1 正确性验证的默认规模（省时间）

- 正确性优先 **N ≤ 12 / dim ≤ 4096**、1–2 条键、短时窗（≤ 2 ns 量级的等效短程）；
  MPS 用 `chi_max ≤ 64`，只在需要收敛性时加到 128。
- 能用解析解/独立稠密参考的，不用大系统"看起来对"来代替。
- 大系统只用于性能基准或用户明确要求的生产验证，且单独跑、单独记录；
  不把它塞进每次迭代的核心判据。
- 新增判据必须能在 `--smoke` 的秒级预算内跑完；更宽的放 core/fast，慢基准放 `--slow`。

## 6. 反模式清单

1. 同一个量有两份实现（两套 Pauli、两套 XOR 翻转、两套测量循环）。
2. schema/GUI/测试各手抄一份后端名单，彼此漂移。
3. 为了一个实验加一个专用键/专用算符名。
4. `**kwargs` 吞掉不支持的选项，静默使用默认值。
5. 未计算的量填 0；缺失值伪装成物理零。
6. 近似后端与纯态共用字段，不标 `approximation`。
7. 无条件把大 H 稠密化，或先建全空间再切片。
8. 热路径里每步重建索引/掩码/`arange`。
9. 为兼容保留永不执行的旧分支和 shim。
10. 新模块没有消费者，或只被一个实验脚本调用。
11. 测试只覆盖对称全 g 初态，掩盖原子顺序/符号错误。
12. 文档宣称"唯一真源/不静默"，代码里却有第二份或静默分支。

## 7. 评审清单（提交前逐条自问）

1. 这个改动属于哪一类？类级能力是否已经存在？我是不是在造第二个定义？
2. 默认不启用时，旧结果是否逐位不变？
3. 不支持的组合是否会**报错并给替代**？
4. 有没有精确小系统对拍？容差来源是什么？
5. 有没有一个运行时不变量能在出错时抓住？
6. 热路径里还有没有可预计算的映射/可向量化的循环？
7. 内存/维度预算是否在入口检查？会不会物化 `O(2^N)`？
8. 结果字段的形状、单位、轴、语义标注是否进了 `data_schema`？
9. 是否删掉了被替代的旧分支/旧键/旧注释？
10. 文档、能力表、测试是否同源？临时文档是否已并入并删除？
