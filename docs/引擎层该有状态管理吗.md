# 引擎层该有状态管理吗 —— 只论 Re0 沙盒（2026-09-18）

> 使用者判断：**「如果只论物理引擎的话，不该有状态管理吧？这是引入交互后才有的事吧？」**
>
> **本文只论 `D:\desktop\Re0重构`，不涉及旧版本。**

---

## 〇、先把三个词分开（免得混着谈）

| 概念 | 回答的问题 | 是"层"还是"约束" |
|---|---|---|
| **单一真源（SSOT）** | 这个事实**记在哪**？ | **约束 / 性质**（**不是一层**） |
| **语义层** | 这个事实**是什么意思**？ | **层** |
| **状态管理** | 这个值**现在是多少、谁改的**？ | **层** |

**⇒ 不是一个意思。** SSOT 可以作用于**任何一层**——Re0 沙盒已经反复在用：

| 哪一刀 | SSOT 的对象 | 载体 |
|---|---|---|
| 第 1 刀 | 结果契约 | `res['states']`（六个引擎同键） |
| 第 4 刀 | 能级基准 | `static_atom.base_sublevels` |
| 第 7 刀 | 引擎分派 | `runspec._ENGINE_TABLE` |
| 第 11 刀 | 参数**值** | 就地定义在各引擎模块 |

**⇒ 所以：问"引擎层该不该有状态管理"，与"要不要 SSOT"是两个问题。**
前者问的是**层**，后者是**性质**。

---

## 一、结论先说

**使用者是对的。** 引擎的**接口**已经是纯函数式的：

```
runspec.build_run(cache, 快照)  →  RunSpec（纯容器，可 pickle）
runspec.evolve_run(RunSpec)     →  Result
static_atom.build_level_rows(cache, B, groups, cfg, visible, E_vpcm)  →  rows
```

**⇒ 引擎层不该有状态管理；状态管理属于引擎之外**（`RunSpec` 冻结 + 会话覆写）。

**但沙盒里还剩 1 处真状态没清掉。** 见下。

---

## 二、扫了一遍 `src/core/` 的模块级可变全局

| 类别 | 处 | 是不是状态 |
|---|---|---|
| **配置型全局**（改变结果） | **1 处**：`static_atom._AC_UI_CFG` + `set_ac_stark_config()` | ✅ **是状态** |
| **诊断累加器**（读一次清零） | **1 处**：`evolve_mixed._BW_STATS` | ⚠️ 约定式 |
| **记忆化缓存** | **8 处**：`runspec._VDD_MEMO`、`field_build._lifetime_cache`、`static_atom._dipole_partners_cache` / `_DIRECT_SHIFT_CACHE` / `_DIRECT_COUPLING`、`sambe._GL_CACHE` / `_VOLT_RULE_CACHE` | ❌ 不是（同输入必同输出） |
| **常量表** | 6 处：`cost.PAIR_CAL`/`PAIR_MEM_CAL`、`_POL_Q`、`POLARIZATION_Q`、`POLS`、`SOLVE_KWARG`、`_ENGINE_TABLE` | ❌ 不是 |

---

## 三、那 1 处真状态：`_AC_UI_CFG`（**实测**）

`static_atom.py:517` 的注释**自己点名了写入方**：

```python
# 面板级 AC-Stark 精度配置（fields.py 光子块/窗口控件写入；后端缺省时读取）
_AC_UI_CFG = dict(n_photon=None, sos_n_window=None)

def set_ac_stark_config(n_photon=None, sos_n_window=None):
    """设置全局 AC-Stark 精度配置……供静态页面板控件调用"""
```

**实测：同一份输入，只因之前调过这个 setter，结果不同——**

| 之前的调用 | `rows[0]['ac']` |
|---|---|
| 没调过（缺省） | **+9.781766 MHz** |
| `set_ac_stark_config(n_photon=2, sos_n_window=40)` | **+1.245223 MHz**（差 **7.9 倍**） |
| `set_ac_stark_config(n_photon=6, sos_n_window=200)` | **申请 13.7 GiB → OOM** |

**三条性质，全是状态管理的坏味道**：

1. **同输入不同输出** ⇒ 引擎不再可复现（除非连"谁调过 setter"一起记）
2. **无作用域、无还原**（`static_atom` 里没有 `reset_*`）⇒ 谁调过就**永久生效**
3. **无校验** ⇒ `n_photon=6` + `sos_n_window=200` 直接把进程撑爆
   （GUI 上一个下拉框就能触发）

**⇒ 而且它来自交互**——注释里的 `fields.py` 是 GUI 面板。
**这正是使用者说的「引入交互后才有的事」，代码自己承认了。**

---

## 四、那 8 处缓存为什么不算状态管理

**判据：同输入必同输出。** 缓存只影响"算多久"，不影响"算出什么"。

**但它们不是没有代价**：

- **进程内、跨 run 存活**（并行扫描里每个 worker 一份）
- **无界或粗暴兜底**：`_VDD_MEMO` 是 `if len > 8: clear()`——**一次全清**，
  不是 LRU；`_DIRECT_SHIFT_CACHE` 有 `MAX=64`；`_GL_CACHE` 没看到上界

**⇒ 缓存该留，但"上界策略"值得统一**（不属本次重构的硬骨头）。

---

## 五、这是第 11 刀的漏网

第 11 刀消灭了 `params.py`（**显式**注册表），并把参数**就地定义**。
但我**只扫了显式注册表，没扫"模块级可变全局"** ⇒
`_AC_UI_CFG` 是一个**从未进过注册表的隐形全局配置**。

**⇒ 同一类病（全局可变配置渗进引擎），第 11 刀治了显式的那半，漏了隐形的这半。**

---

## 六、怎么清 —— **`_AC_UI_CFG` 已清（2026-09-19）**

> ✅ **已执行**：删 `_AC_UI_CFG` + `set_ac_stark_config()`；改成就地常量 `AC_N_PHOTON` / `AC_SOS_N_WINDOW` + **显式传参**（`build_level_rows` 加两个形参一路透传）；并加**内存闸** `AC_NM_MAX=12000`。
> **实测**：同输入连调三次**逐位相同**；显式传参改精度后，缺省**未被污染**；原来 OOM 的组合现在报 `ValueError`；`n_photon=0` / `sos_n_window=-1` 也被挡。
> ⚠ 代价：`sos_n_window=100`（nph=4）现在被闸住（≈8 GiB）——要放开就显式提高 `AC_NM_MAX`（报错信息里写了）。

### 以下是当时的方案（保留作记录）

### `_AC_UI_CFG` → 删全局，缺省就地定义

两个消费函数**本来就有形参**：

```python
direct_ac_stark_shifts(cache, groups, address_cfg, B_gauss,
                       n_photon=None, sos_n_window=None)   # None 时读全局
```

**⇒ 把"读全局"那半删掉**，缺省写成本模块常量（和参数就地定义同款）：

```python
AC_N_PHOTON = 4          # 光子块阶数（缺省）
AC_SOS_N_WINDOW = None   # 偶极伙伴窗口（None = 不裁剪）
```

调用方（GUI 面板）**显式传**。`set_ac_stark_config()` 删除。

**顺带解决第 3 条**：缺省值就地定义后，可以在那里加**上界校验**
（`n_photon` × `sos_n_window` 撑爆空间这件事，本来就该在入口挡住）。

### `evolve_mixed._BW_STATS` → 走 `error_report` 返回

它现在是"运行内累加、读一次清零"的手工传递。结果里**已经有 `error_report`**，
把它放进去即可（不再靠模块级约定）。

### 缓存 → **不动**

它们不是状态管理。只在将来统一"上界策略"时再看。

## 七、一句话

> **引擎层 = 纯函数 + 记忆化；状态管理 = 引擎之外（`RunSpec` 冻结 + 会话覆写）。**
>
> **沙盒已经基本做到——只剩 `_AC_UI_CFG` 一处漏网，而它恰好是"交互渗进引擎"的标本
> （注释自己写着写入方是 GUI 面板）。**
