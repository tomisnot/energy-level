## 第 7 刀：参数白名单改"签名派生"（原第一批 #3）

### 改前

```
SOLVE_KWARG              solve.* → kwarg 映射（手抄）
god_kwargs_from_params   全量收 solve.*/engine.*
_filter_kw(d, allow)     按白名单筛；allow 来自
    _MIXED_PAIR_KW / _MIXED_SINGLE_KW / _HARD_KW    ← 照引擎签名手抄
```

三层里两层手抄。`max_step_hard` 那个洞就是这么来的：`SOLVE_KWARG` 里**已经**有映射，
参数一路收上来却在最后一跳被整包丢掉，旧文案只好写"请经库 API 直调 `hard.evolve_hard`"。

### 改后

```python
_ENGINE_TABLE = {                     # (method, two_body) → 引擎函数。**唯一分派表**
    ('mixed', False): ('.evolve_mixed', 'evolve_mixed'), ...
}

def engine_fn(method, two_body): ...           # 查询口（惰性 import）
def _engine_accepts(fn, key):                  # 就是查签名形参名（六个引擎都没有 **kwargs）
    return key in inspect.signature(fn).parameters
def _filter_kw(fn, d): ...                     # 白名单 = 签名本身
```

三个 `_XXX_KW` 常量删除；`build_run` 的两处筛参改为 `_filter_kw(engine_fn(meth, tb), ek_all)`；
`evolve_run` 的六处 `from .X import Y` 改为走 `fn = engine_fn(meth, tb)`（分支只负责"备料"）。

### 等价性验证（实测）

对 `solve.*` 能产出的 6 个 kwarg，逐 (method, two_body) 比对"签名收的"与"旧手抄白名单收的"：

| (method, two_body) | 一致？ |
|---|---|
| `mixed` 单体 / 两体 | ✅ 逐键一致 |
| `hard` 单体 / 两体 | ✅ 逐键一致 |
| `sambe` 单体 / 两体 | **不一致**——签名里**确实有** `tol`/`frozen_h_ns`，旧手抄表写的是"sambe 什么都不收"（**是错的**） |

`sambe` 那处差异是**惰性**的：`evolve_run` 的两条 sambe 分支都**只传显式参数、不传 `**_ek`**
⇒ `ek` 从不进 sambe。**基线 16/0 全绿证明无行为变化。**

|---|---|---|---|

| `_embed` / `_reconstruct` | `sambe.embed` / `sambe.reconstruct_psi`（**公开名**） | `sambe._embed`/`_reconstruct`（两行包装）+ `evolve_twofield` 的两份（内联重写） | 见下 |

### `_embed` / `_reconstruct` 的真相（这一步差点做错）

`evolve_twofield` 那份用 `setup.N`，正本用 `setup.N2`/`n_phys`。**先以为是"滞后拷贝"，实测
`sambe.py:108-110`**：

```python
self.n_phys = E.size
self.N = self.n_phys          # 单体引擎消费名
self.N2 = self.n_phys         # 两体引擎消费名
```

⇒ 三者**同一个值**，所以两份等价。

**但合并后立刻红了**：`_TwoFieldSetup` **只有 `N`，没有 `N2`/`n_phys`** ⇒
`AttributeError`。**这才是那份重复真正存在的原因——两个 setup 对象的接口不一致。**

**正解不是硬塞，是统一协议**：给 `_TwoFieldSetup` 补 `n_phys`/`N2` 别名，
并在类 docstring 写明"与 `SambeSetup` 共用扩展空间协议（`N`/`n_phys`/`N2` + `P`/`p_center`/
`dim`/`nphase`）——`sambe.embed`/`reconstruct_psi` 同时吃两种 setup，靠的就是这组名字一致"。

顺带收掉 `sambe._embed_pair = embed` 这个**兼容别名**（GPU 模块在用）。

## 第 9 刀：`diag` 消息不再怪调用方（原第一批 #7）

`diag.summarize(None)` 原文：**「无诊断快照（diag=True 才有）」**——而调用方**确实**传了
`diag=true`（`runspec.py:221` 就设了）。真相是**只有 mixed 家族产出诊断**。

改为：`summarize(None, {'method': 'hard'})` → **「method=hard 不产出诊断快照——诊断当前
只有 mixed 引擎产出（传 diag=True 也不会改变这一点）」**。
`diag.py` 模块头也写明了归属。

## 两条自我更正

### ① 病症【H】撤回：`torch` 不是问题

原判断"`evolve_sambe_pair_gpu.py` 顶层 import torch ⇒ 整个 `src/core` 硬依赖 GB 级包"。
**实测推翻**：

```
import src.core                        0.95 s   torch 被拉入: False
import src.core.evolve_sambe_pair_gpu   7.54 s   torch 被拉入: True
```

`sambe.py:1559` 的 import **在函数体内**，只有真走 GPU 路径才触发。**没有东西要改**；
只在模块 docstring 补了一句"本模块是 torch 的唯一入口"。

### ② 我的操作错误：后台基线期间改了引擎

曾启动后台基线后继续改 `sambe.py`/`evolve_twofield.py` ⇒ 那次基线跑的是**半途修改的树**，
报了一个**假红**（`evolve_exact_pair_selfcheck`）。
**教训：跑基线期间不要动引擎**——已在流程里避免。
